# 基金分析 Agent（Java 版）第二部分开发指引

> 阶段：Phase 1——真实基金数据接入与数据底座  
> 前置：Phase 0 已完成多模块骨架、Mock 查询链路、本机 MySQL、Redis、Flyway 和基础测试。  
> 目标：将 Mock 查询升级为“可采集、可校验、可落库、可缓存、可追溯、可降级”的真实基金数据链路。  
> 本阶段仍不接入大模型，不实现 Agent、收益分析、用户持仓和投资建议。

## 1. 为什么第二部分先做数据底座

基金 Agent 的回答质量首先取决于事实数据。若直接让大模型调用第三方网页，会产生以下问题：

- 第三方接口变化会直接导致 Agent 失效。
- 同一个问题在不同时间返回的数据口径可能不一致。
- 无法说明净值来自哪里、何时采集、是否过期。
- 无法稳定复算收益率、最大回撤等指标。
- 外部数据源超时后没有缓存与降级能力。
- 测试依赖公网，结果不可重复。

因此本阶段建立一条稳定链路：

```text
第三方基金数据源
        ↓
ExternalFundDataProvider（采集端口）
        ↓
数据标准化 + 质量校验
        ↓
FundRepository / FundNavRepository
        ↓
MySQL（事实数据）
        ↓
Redis（查询缓存）
        ↓
FundQueryUseCase
        ↓
REST API / 后续 Agent Tools
```

关键原则：大模型、Controller 和定时任务都不能直接解析第三方响应。

## 2. 本阶段交付结果

完成后，项目必须具备以下能力：

1. 通过一个真实数据源获取基金基本信息和历史净值。
2. 将第三方字段转换为项目内部统一模型，不泄漏第三方 DTO。
3. 基金与净值数据写入本机 MySQL，重复同步不会产生重复数据。
4. 查询 API 默认读取数据库，并使用 Redis 缓存热点数据。
5. 数据源超时、限流或结构异常时有重试、熔断和明确错误码。
6. 每条数据能够追溯 `dataSource`、`sourceUpdatedAt`、`collectedAt`。
7. 支持手动同步和定时增量同步。
8. 保留 Mock Provider，使开发和测试不依赖公网。
9. 对同步成功率、耗时、数据新鲜度和失败原因提供指标。
10. 自动化测试不访问真实第三方接口。

## 3. 数据范围与业务口径

本阶段只处理公募基金的基础信息和日净值：

```text
基金代码
基金名称
基金类型
基金公司
基金经理
成立日期
单位净值
累计净值
净值日期
数据来源
来源更新时间
本系统采集时间
```

需要明确：普通开放式基金没有真正的盘中实时净值，正式净值通常按交易日更新；盘中看到的多数是估算值。ETF 的盘中行情属于另一套证券行情链路。本阶段只保存已确认的日净值，不把估算值伪装成正式净值。

本阶段暂不保存：

- 盘中估值和 ETF Tick/K 线。
- 基金持仓明细、基金公告和新闻。
- 用户自选、交易和持仓。
- 收益率、波动率、夏普比率、最大回撤。
- 模型生成的结论。

## 4. 数据源接入策略

### 4.1 优先级

真实数据获取优先使用：

1. 有明确授权和 SLA 的基金/金融数据 API。
2. 基金公司、交易所等公开且允许程序访问的接口。
3. 公开网页接口仅用于个人学习和验证，必须遵守网站条款、robots、频率限制与数据授权要求。

不要把 HTML 爬虫作为领域核心。若当前只能使用公开网页接口，也必须把解析逻辑隔离在 Infrastructure Adapter 中，以便随时替换。

### 4.2 配置

```yaml
fund:
  provider:
    type: real
    base-url: ${FUND_DATA_BASE_URL}
    api-key: ${FUND_DATA_API_KEY:}
    connect-timeout: 2s
    read-timeout: 5s
    max-retries: 2
  sync:
    enabled: true
    cron: "0 30 2 * * MON-FRI"
    batch-size: 100
  cache:
    profile-ttl: 6h
    latest-nav-ttl: 30m
    history-ttl: 2h
```

API Key、Cookie、Token 不得进入 Git、日志、异常消息或数据库原始响应。

### 4.3 外部数据端口

Phase 0 的 `FundDataProvider` 同时承担了“查询数据”和“访问外部数据源”两个职责。本阶段应拆分：

```java
public interface ExternalFundDataProvider {
    Optional<ExternalFundProfile> fetchProfile(FundCode fundCode);

    List<ExternalNavPoint> fetchNavHistory(
        FundCode fundCode,
        LocalDate startDate,
        LocalDate endDate
    );

    String sourceName();
}
```

`ExternalFundProfile`、`ExternalNavPoint` 是标准化后的领域输入，不是第三方 JSON DTO。第三方 DTO 只能存在于 `fund-infrastructure`。

建议实现：

```text
MockExternalFundDataProvider       测试和离线开发
HttpExternalFundDataProvider       真实 HTTP 数据源
```

不要在本阶段同时接入多个真实数据源。先把一个数据源做稳定，再在后续增加主备 Provider 和交叉校验。

## 5. 领域模型和端口调整

### 5.1 模型补全

```java
public record FundProfile(
    FundCode code,
    String name,
    String fundType,
    String managementCompany,
    String fundManager,
    LocalDate establishedDate,
    String dataSource,
    Instant sourceUpdatedAt,
    Instant collectedAt
) {}

public record NavPoint(
    FundCode fundCode,
    LocalDate navDate,
    BigDecimal unitNav,
    BigDecimal accumulatedNav,
    String dataSource,
    Instant sourceUpdatedAt,
    Instant collectedAt
) {}
```

约束：

- `unitNav`、`accumulatedNav` 必须大于 0。
- 数值统一使用 `DECIMAL` / `BigDecimal`。
- `navDate` 代表净值归属日期，`collectedAt` 代表本系统采集时间，不能混用。
- 第三方没有提供来源更新时间时，允许 `sourceUpdatedAt` 为空，但不能伪造。
- 基金代码仍由 `FundCode` 统一校验。

### 5.2 Repository 端口

在 `fund-domain` 定义，不依赖 MyBatis：

```java
public interface FundRepository {
    Optional<FundProfile> findByCode(FundCode fundCode);

    void save(FundProfile fundProfile);

    List<FundCode> findEnabledFundCodes(int offset, int limit);
}

public interface FundNavRepository {
    List<NavPoint> findHistory(
        FundCode fundCode,
        LocalDate startDate,
        LocalDate endDate
    );

    Optional<NavPoint> findLatest(FundCode fundCode);

    int upsertBatch(List<NavPoint> navPoints);
}
```

Repository 只表达业务需要，不暴露 `QueryWrapper`、分页插件或数据库 Entity。

### 5.3 同步用例

在 `fund-application` 新增：

```java
public interface FundSyncUseCase {
    FundSyncResult syncFund(String fundCode, LocalDate startDate, LocalDate endDate);

    BatchSyncResult syncEnabledFunds(LocalDate startDate, LocalDate endDate);
}
```

`FundSyncApplicationService` 的顺序必须固定：

```text
校验输入
  → 获取同步锁
  → 调用 ExternalFundDataProvider
  → 标准化与质量校验
  → 事务写入基金和净值
  → 记录同步审计
  → 提交事务
  → 删除相关缓存
  → 释放同步锁
```

缓存失效必须发生在数据库事务成功后。同步失败不得删除当前可用缓存。

## 6. MySQL 表设计

使用 Flyway 新增 `V2__create_fund_data_tables.sql`，不要修改已经执行过的 `V1`。

### 6.1 fund

```sql
CREATE TABLE fund (
    id BIGINT NOT NULL AUTO_INCREMENT,
    fund_code VARCHAR(6) NOT NULL,
    fund_name VARCHAR(128) NOT NULL,
    fund_type VARCHAR(64) NULL,
    management_company VARCHAR(128) NULL,
    fund_manager VARCHAR(128) NULL,
    established_date DATE NULL,
    enabled TINYINT(1) NOT NULL DEFAULT 1,
    data_source VARCHAR(64) NOT NULL,
    source_updated_at DATETIME(3) NULL,
    collected_at DATETIME(3) NOT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_fund_code (fund_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 6.2 fund_nav

```sql
CREATE TABLE fund_nav (
    id BIGINT NOT NULL AUTO_INCREMENT,
    fund_code VARCHAR(6) NOT NULL,
    nav_date DATE NOT NULL,
    unit_nav DECIMAL(18,6) NOT NULL,
    accumulated_nav DECIMAL(18,6) NULL,
    data_source VARCHAR(64) NOT NULL,
    source_updated_at DATETIME(3) NULL,
    collected_at DATETIME(3) NOT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_fund_nav_code_date (fund_code, nav_date),
    KEY idx_fund_nav_date (nav_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

数据库唯一键是幂等同步的最后防线。不能采用“先删区间、再批量插入”的方式更新历史净值。

### 6.3 fund_sync_record

在 `V3__upgrade_fund_sync_record.sql` 中补充：

```text
sync_type              PROFILE / NAV / FULL
date_range_start
date_range_end
requested_count
saved_count
sync_status            RUNNING / SUCCESS / FAILED / PARTIAL
error_code
error_message           截断后的安全错误，不保存第三方完整响应
started_at
finished_at
```

同步记录用于审计和故障排查，不参与基金事实查询。

## 7. MyBatis-Plus 实现

在 `fund-infrastructure` 引入与当前 Spring Boot 兼容的 MyBatis-Plus Starter，并创建：

```text
infrastructure/persistence/entity/FundEntity.java
infrastructure/persistence/entity/FundNavEntity.java
infrastructure/persistence/entity/FundSyncRecordEntity.java
infrastructure/persistence/mapper/FundMapper.java
infrastructure/persistence/mapper/FundNavMapper.java
infrastructure/persistence/mapper/FundSyncRecordMapper.java
infrastructure/persistence/repository/MybatisFundRepository.java
infrastructure/persistence/repository/MybatisFundNavRepository.java
```

映射规则：

- Entity 只属于 Infrastructure。
- Domain Model 不添加 MyBatis 注解。
- Mapper 不允许被 Controller、Agent Tool 直接注入。
- Entity 与 Domain 的转换集中在 Mapper/Assembler，禁止散落在业务代码中。
- 批量 upsert 使用明确 SQL，并校验批次大小，不能循环逐条提交事务。

MySQL upsert 示例：

```sql
INSERT INTO fund_nav (...)
VALUES (...), (...)
ON DUPLICATE KEY UPDATE
    unit_nav = VALUES(unit_nav),
    accumulated_nav = VALUES(accumulated_nav),
    data_source = VALUES(data_source),
    source_updated_at = VALUES(source_updated_at),
    collected_at = VALUES(collected_at);
```

## 8. HTTP 客户端、容错与限流

### 8.1 HTTP Adapter

使用 Spring `RestClient` 或 `WebClient`，二选一。当前项目是 Spring MVC，同步采集优先选择 `RestClient`，避免为了单个数据源引入全响应式链路。

Adapter 必须实现：

- 连接超时和读取超时。
- User-Agent 和必要鉴权头。
- HTTP 状态检查。
- 响应体大小限制。
- JSON 字段缺失和类型变化处理。
- 第三方错误转换为项目内部异常。
- 日志脱敏。

禁止把第三方原始异常直接抛到 Controller。

### 8.2 重试

仅对以下情况重试：

```text
连接超时
读取超时
HTTP 429
HTTP 502 / 503 / 504
```

以下情况不重试：

```text
参数错误
基金不存在
鉴权失败
响应结构无法解析
数据质量校验失败
```

最多重试 2 次，使用指数退避并加入随机抖动。禁止无限重试。

### 8.3 熔断与限流

使用 Resilience4j：

- 按数据源维度设置 Circuit Breaker。
- 限制每秒请求数和并发数。
- 暴露熔断状态与失败计数指标。
- 熔断后停止主动请求，查询继续使用数据库中的最后可用数据。

降级时响应必须保留原始 `collectedAt`，让调用者知道数据可能过期，不能用当前时间冒充新数据。

## 9. Redis 缓存设计

缓存只提升查询性能，MySQL 始终是本阶段的事实数据源。

### 9.1 Key 规范

```text
jijing:fund:profile:{fundCode}
jijing:fund:nav:latest:{fundCode}
jijing:fund:nav:history:{fundCode}:{startDate}:{endDate}
jijing:fund:sync-lock:{fundCode}
```

### 9.2 策略

- 使用 Cache Aside：先查缓存，未命中再查数据库并回填。
- Profile TTL 建议 6 小时，最新净值 30 分钟，历史区间 2 小时。
- TTL 增加随机抖动，避免同一时刻大量失效。
- 基金不存在使用 1～5 分钟的短空值缓存，防止缓存穿透。
- 同步成功后按基金代码删除相关缓存。
- Redis 不可用时直接查 MySQL，不能导致查询 API 整体失败。
- 历史区间 Key 数量可能膨胀；本阶段限制查询区间最长 5 年，并设置统一前缀和 TTL。

不要把第三方原始 JSON 放入 Redis。缓存项目自己的稳定响应模型。

## 10. 查询链路调整

Phase 0：

```text
QueryUseCase → MockFundDataProvider
```

Phase 1：

```text
QueryUseCase
  → FundQueryCache
  → FundRepository / FundNavRepository
  → MySQL
```

外部 Provider 只由同步用例调用：

```text
FundSyncUseCase
  → ExternalFundDataProvider
  → Repository
```

这样即使第三方数据源宕机，已有数据仍可查询，未来 Agent 的工具调用也不会被外部网站稳定性直接拖垮。

查询响应建议新增：

```json
{
  "fundCode": "000001",
  "name": "示例基金",
  "dataSource": "provider-a",
  "sourceUpdatedAt": "2026-08-22T22:00:00Z",
  "collectedAt": "2026-08-22T22:05:12Z",
  "freshness": "FRESH"
}
```

`freshness` 由系统根据业务阈值计算：

```text
FRESH       在预期更新时间内
STALE       已超过预期更新时间，但仍可展示
UNKNOWN     无法判断来源更新时间
```

不要因为周末和节假日没有新净值就直接判断为异常。

## 11. 同步任务

在 `fund-scheduler` 实现调度入口，在 `fund-application` 实现同步业务。Scheduler 不能直接调用 Provider 或 Mapper。

第一版使用 Spring Scheduling 即可：

```java
@Scheduled(cron = "${fund.sync.cron}", zone = "Asia/Shanghai")
public void syncDailyNav() {
    fundSyncUseCase.syncEnabledFunds(...);
}
```

要求：

- 本地可通过配置关闭定时任务。
- 任务按基金分页，禁止一次加载全部基金。
- 每个基金独立记录成功或失败，单个失败不能中断整批。
- 同一个基金同一时间只允许一个同步任务。
- 使用 Redis/Redisson 分布式锁，必须设置租约和唯一 owner。
- 锁获取失败代表已有任务运行，不算数据源失败。
- 增量同步从数据库最新净值日期向前回看 3～5 个交易日，允许第三方修正历史值。
- 任务重启后能够继续运行，不能依赖 JVM 内存保存进度。

本地调试可增加仅在 `local` Profile 生效的手动同步接口：

```text
POST /internal/v1/funds/{fundCode}/sync?startDate=2026-01-01&endDate=2026-08-01
```

该接口不得在生产 Profile 暴露，也不能被 Agent Tool 注册。

## 12. 数据质量校验

写库前至少检查：

- 基金代码与请求代码一致。
- 基金名称不为空。
- 净值日期位于请求区间内，且不晚于合理业务日期。
- 单位净值大于 0。
- 同一批数据不存在相同 `fundCode + navDate` 的冲突记录。
- 日期按升序整理后写库。
- 单日净值异常跳变只告警，不直接擅自修正。
- 第三方返回空列表时区分“正常无交易数据”和“响应异常”。

对异常数据执行：

```text
拒绝写入
记录 DATA_QUALITY_ERROR
增加质量失败指标
保留数据库中上一版有效数据
```

禁止静默把空字符串变成 0，禁止用前一天净值填补未知数据。

## 13. API 与错误码

保留 Phase 0 查询接口：

```text
GET /api/v1/funds/{fundCode}
GET /api/v1/funds/{fundCode}/nav?startDate=...&endDate=...
```

增加或补齐错误码：

| 业务码 | HTTP | 含义 |
| --- | ---: | --- |
| INVALID_ARGUMENT | 400 | 基金代码或日期范围非法 |
| FUND_NOT_FOUND | 404 | 本地和允许触发的上游均无该基金 |
| DATA_NOT_READY | 409 | 基金存在，但尚未完成初次同步 |
| DATA_SOURCE_RATE_LIMITED | 503 | 上游限流 |
| DATA_SOURCE_UNAVAILABLE | 503 | 上游超时、熔断或不可用 |
| DATA_QUALITY_ERROR | 502 | 上游返回的数据不满足质量规则 |
| SYNC_ALREADY_RUNNING | 409 | 同基金同步任务正在执行 |

查询接口不应每次触发外部同步。若本地没有数据，可返回 `DATA_NOT_READY`，由同步任务或本地手动同步接口负责采集。

## 14. 可观测性

新增指标：

```text
fund_provider_request_total{provider,result}
fund_provider_request_duration_seconds{provider,operation}
fund_sync_total{provider,result}
fund_sync_saved_records_total{provider}
fund_data_quality_failure_total{provider,rule}
fund_cache_request_total{cache,result}
fund_data_freshness_seconds{fundCode}
```

注意 `fundCode` 可能产生高基数。开发阶段可以保留，生产指标应只对白名单基金使用标签，或者改为日志字段。

同步日志至少包含：

```text
syncId / fundCode / provider / dateRange / fetchedCount /
savedCount / durationMs / result / errorCode
```

第三方响应正文只允许在本地调试以脱敏、截断形式记录，生产默认禁止。

## 15. 测试策略

### 15.1 Domain

- 净值必须大于 0。
- 来源时间、采集时间的边界。
- 重复日期检测。
- 数据新鲜度计算，覆盖周末场景。

### 15.2 Application

- 同步成功后保存 Profile、Nav 和审计记录。
- 数据校验失败时不写入数据库。
- 数据库事务失败时不删除缓存。
- 同步锁未获取时返回稳定结果。
- 查询缓存命中、未命中、Redis 异常降级。
- 数据源异常映射为正确业务错误。

### 15.3 Infrastructure

使用 `MockWebServer` 模拟第三方接口，覆盖：

- 正常 JSON。
- 字段缺失或类型变化。
- 404、429、500、503。
- 超时与重试次数。
- 响应体过大。
- API Key 不出现在日志中。

使用独立 `jijing_agent_test` 数据库验证：

- Flyway V1～V3 能在空库执行。
- 同一净值写入两次仍只有一条记录。
- 同一日期的修订值可以被 upsert 更新。
- 日期区间查询使用正确索引。
- 事务失败不会留下半批数据。

测试开始前必须检查数据库名等于 `jijing_agent_test`，否则立即失败。

### 15.4 禁止事项

- 自动化测试禁止请求真实公网数据源。
- 测试禁止使用开发库 `jijing_agent`。
- 测试之间禁止依赖执行顺序。
- 不用 `Thread.sleep` 等待异步结果，使用可控 Clock 或 Awaitility。

## 16. 推荐开发顺序

每一步保持可编译、可测试：

1. 引入 MyBatis-Plus、MockWebServer、Resilience4j、Redisson，并锁定兼容版本。
2. 新增 V2、V3 Flyway 脚本和测试库保护配置。
3. 补全 Domain 模型，新增 Repository 和 External Provider 端口。
4. 实现 MyBatis Entity、Mapper、Repository 和领域转换。
5. 将现有查询用例改为数据库查询，并保持 API 兼容。
6. 实现 MockExternalFundDataProvider 和同步应用服务。
7. 使用 MockWebServer 完成真实 HTTP Adapter 的契约测试。

## 17. 完成标准

只有同时满足以下条件，Phase 1 才算完成：

- `mvn clean verify` 全部通过。
- V1～V3 能在空的本机数据库自动迁移成功。
- 一个真实基金可以同步 Profile 和至少一年的历史日净值。
- 重复执行同步不会产生重复记录。
- 查询接口只依赖缓存和 Repository，不直接调用第三方数据源。
- Redis 停止时查询仍能从 MySQL 返回数据。
- 第三方接口超时、429、5xx 和字段变化均有自动化测试。
- 数据源不可用时，已有数据仍然可查询，并标明数据采集时间和新鲜度。
- 日常同步任务支持开关、分页、锁、增量回看和失败审计。
- 项目中不存在真实密码、Cookie、Token 和 API Key。
- README 中能够让新开发者独立完成建库、同步和查询验证。
