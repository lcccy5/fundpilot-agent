# FundScope Go 版后续版本开发大纲（V2～V6）

> 基线：V1 已形成可运行的单机闭环，包括真实基金 Provider、SQLite/MySQL、Redis 可选缓存、基金指标、多基金比较、自选与持仓、Tool Calling、DAG、HITL、知识库、SSE、Prometheus 和 Web 页面。

## 1. 版本总览

V1 之后建议再开发 5 个主要版本。每一版都必须可以独立发布和验收，不能把所有功能堆到最后一次发布。

| 版本 | 主题 | 解决的核心问题 | 主要简历价值 |
| --- | --- | --- | --- |
| V2 | 数据可信与用户产品化 | 数据源单一、身份和业务功能仍偏单机 | 数据工程、缓存、权限、可靠性 |
| V3 | Agent Runtime 2.0 | 当前 Agent 计划与状态管理还不够完整 | Tool Calling、持久化 DAG、HITL、AgentOps |
| V4 | RAG 2.0 与研究工作台 | 本地检索适合小数据，文档治理和评测不足 | 混合检索、向量库、重排、引用治理 |
| V5 | 组合智能与主动助手 | 当前偏被动问答，组合分析深度有限 | 风险引擎、事件驱动、主动 Agent、多 Agent |
| V6 | 生产级与平台化 | 单机可用，但尚未达到多人和高可用平台标准 | 分布式、可观测性、安全、SRE、成本治理 |

推荐顺序：

```text
V1 单机闭环
→ V2 数据可信
→ V3 Agent 可控执行
→ V4 知识可信
→ V5 主动组合助手
→ V6 生产平台
```

不能为了展示 Agent 而跳过 V2。基金项目中，数据不可信会让后续 Agent、RAG 和组合分析全部失去意义。

## 2. V2：数据可信与用户产品化

### 2.1 版本目标

把 V1 从“单用户可用工具”升级为“数据可靠、账户清晰、可以日常使用的基金产品”。

### 2.2 数据能力

1. 多数据源 Provider：
   - 主 Provider；
   - 备用 Provider；
   - 手工导入 CSV；
   - 标准 HTTP 商业数据源适配器；
   - Provider 健康度评分和自动降级。
2. 数据分类：
   - 基金公司确认净值；
   - 盘中估值；
   - 基金资料；
   - 基金持仓；
   - 基金经理和管理人；
   - 交易日历；
   - 分红、拆分和份额变更。
3. 数据质量规则：
   - 净值必须为正数；
   - 交易日期不能重复；
   - 日期不能超过当前时间；
   - 单日异常跳变需要标记；
   - 累计净值异常回退需要检查分红和复权；
   - 多数据源差异超过阈值时进入隔离区。
4. 数据版本和血缘：
   - `provider`；
   - `source_updated_at`；
   - `collected_at`；
   - `batch_id`；
   - `payload_hash`；
   - `data_version`；
   - 修订前后的版本关系。
5. 同步治理：
   - 全量初始化；
   - 工作日增量同步；
   - 失败重试和死信记录；
   - 同一基金幂等锁；
   - 数据新鲜度检测；
   - 上游接口变更告警。

### 2.3 用户产品能力

- 用户注册和登录；
- JWT Access Token + Refresh Token；
- 密码使用 Argon2id 或 bcrypt；
- 用户、管理员和只读角色；
- 自选基金分组和标签；
- 多个持仓组合；
- 交易流水导入，不直接执行交易；
- 分红方式、手续费和成本修正；
- 用户数据导出与注销；
- 用户之间的自选、持仓和私有文档严格隔离。

### 2.4 工程技术点

- MySQL Migration 正式版本管理；
- `sqlc` 或显式 Repository 查询；
- Redis Cache Aside；
- 分布式锁与 Singleflight；
- Provider 限流、指数退避、熔断；
- Asynq 或消息队列执行同步任务；
- 审计日志脱敏；
- OpenAPI 文档和前后端类型生成。

### 2.5 V2 验收标准

- 任意同步任务重复执行不会产生重复净值；
- 主数据源故障时自动使用备用源或已有数据降级；
- 响应明确返回数据来源、确认/估值状态和更新时间；
- 数据过期时页面和 Agent 都能明显提示；
- 两个测试用户不能读取对方持仓和私有文档；
- 交易流水导入后成本和收益能够复算；
- 固定数据集的来源一致性目标达到 99.5% 以上；
- Provider 契约变化能够触发自动化测试失败和告警。

### 2.6 推荐周期

专注开发约 2～4 周；边学 Go 边开发约 4～7 周。

## 3. V3：Agent Runtime 2.0

### 3.1 版本目标

把 V1 的 Tool Calling 升级为可暂停、可恢复、可重试、可评测的受控 Agent Runtime。这一版是简历中最重要的 Agent 版本。

### 3.2 Agent 框架

- 使用 Eino 接入 ChatModel、Tool、Callback 和流式模型；
- 保留项目自己的基金 Agent Runtime；
- Eino 负责模型与组件适配；
- 项目负责权限、状态、审计、证据和业务执行限制；
- 模型未配置或失败时保留确定性路由。

### 3.3 路由模式

```text
DIRECT        单工具或确定性回答
PARALLEL      多个无依赖只读工具并行
PLAN_EXECUTE  复杂报告生成任务 DAG
CLARIFY       缺少基金代码、区间或组合时追问
HITL          敏感写操作等待人工决定
REFUSE        收益保证、自动交易和越权请求
```

### 3.4 持久化 DAG

新增或完善：

- `agent_plan`；
- `agent_task`；
- `agent_task_dependency`；
- `agent_tool_call`；
- `agent_checkpoint`；
- `agent_run_event`。

执行要求：

1. Planner 只生成结构化计划；
2. 执行前重新生成内部 ID；
3. 校验 Tool 白名单、参数 Schema 和用户权限；
4. 拓扑排序检测环和未知依赖；
5. 无依赖任务受限并行；
6. 单任务、单批次和整个 Run 分层超时；
7. 父 `context` 取消时终止模型、HTTP、数据库和 Tool；
8. 可重试错误使用指数退避；
9. 依赖失败的任务标记 `SKIPPED`；
10. 只有计划不可执行时才调用 Replanner；
11. 已完成任务不能重复执行；
12. 服务重启后从 Checkpoint 恢复。

### 3.5 Memory

- 当前会话窗口保存在 Redis；
- 超出窗口后生成会话摘要；
- 用户明确确认的偏好写入长期记忆；
- 持仓、净值和风险指标不从模型记忆读取；
- 长期记忆必须支持查看、修改和删除；
- 不同用户和会话严格隔离。

### 3.6 HITL 2.0

- 批准一次；
- 会话内批准同类操作；
- 修改参数后批准；
- 拒绝并给出原因；
- 审批过期；
- 审批后从 Checkpoint 恢复；
- 通知审批人；
- 自动交易永远不进入审批，而是直接禁止。

### 3.7 AgentOps 与评测

固定评测集至少覆盖：

- Tool 选择；
- 参数正确性；
- 日期范围；
- 多基金比较；
- 数据不足拒答；
- 引用完整性；
- 收益保证拦截；
- 越权访问拦截；
- 重复 Tool Call 限制；
- 超时、取消和局部恢复。

记录指标：

- Tool 选择正确率；
- 参数正确率；
- Run 成功率；
- 首事件耗时；
- 首 Token 耗时；
- 总耗时；
- Tool 重试率；
- Token 和模型成本；
- 无证据拒答率；
- HITL 触发和批准比例。

### 3.8 V3 验收标准

- 固定评测集 Tool 选择正确率目标不低于 90%；
- 数值问题与 Analytics 结果一致；
- 重启服务后可以恢复等待审批或执行中的 Run；
- SSE 能按照真实发生顺序返回计划、任务、Tool、审批和回答事件；
- 客户端断开会取消下游任务；
- Agent 不可以直接访问数据库和 Provider；
- Agent 生成的证据 ID 必须存在于本次 Run 的 Evidence 集合；
- `go test -race ./...` 不出现竞争问题。

### 3.9 推荐周期

专注开发约 3～5 周；边学边开发约 5～9 周。

## 4. V4：RAG 2.0 与基金研究工作台

### 4.1 版本目标

把 V1 的本地知识检索升级为可以管理大量基金公告、季报和招募说明书的可信研究系统。

### 4.2 文档摄取

- PDF、HTML、TXT、Markdown；
- Tika 解析与 OCR；
- 文件类型、大小和病毒检查；
- 原文件对象存储；
- 文档、版本和摄取任务状态机；
- 基金代码、文档类型、报告期、发布日期和来源元数据；
- 内容哈希去重；
- 失败重试和死信；
- 新版本索引完成后再原子切换；
- 旧版本可追溯但默认不参与检索。

### 4.3 检索架构

```text
Query Rewrite
→ 权限和元数据过滤
→ BM25 召回
→ Dense Vector 召回
→ RRF 融合
→ Cross-Encoder / LLM Rerank
→ 邻居块扩展
→ Context Budget
→ 页码级 Citation
```

推荐组件：

- Elasticsearch/OpenSearch：BM25、向量和过滤；
- Embedding Provider 抽象；
- 批量向量化和失败重试；
- 可选本地 Embedding；
- Reranker Provider 抽象；
- Redis Query Cache；
- 对象存储 MinIO/S3。

### 4.4 引用治理

- Evidence 只能由 Retriever 创建；
- 回答引用必须匹配 `document_id + version + page + chunk_id`；
- 模型生成的未知引用直接判失败；
- 文档删除或权限变化后引用立即失效；
- 实时数据引用与文档引用采用不同类型；
- 页面支持点击引用跳到原文位置。

### 4.5 RAG 安全

- 文档内容始终视为不可信数据；
- 文档中的“忽略系统指令”不能影响 Agent；
- 私有文档权限过滤必须在检索阶段完成；
- 禁止仅靠 Prompt 做租户隔离；
- OCR 和 PDF 解析放在隔离 Worker；
- 限制压缩炸弹、超大页数和超长文本；
- 对上传、下载、检索和导出进行审计。

### 4.6 RAG 评测

- 文档级 Recall@K；
- Chunk Recall@K；
- MRR / NDCG；
- 引用准确率；
- 引用覆盖率；
- 忠实度；
- 无答案拒答率；
- 私有文档越权率必须为零；
- Prompt Injection 攻击成功率目标为零。

### 4.7 V4 验收标准

- 同一文档重复上传不会重复建立正式索引；
- 新版本未完成时旧版本继续可用；
- 固定评测集 Recall@5 目标达到 85% 以上；
- 引用准确率目标达到 95% 以上；
- 回答中的所有引用都能打开到真实原文；
- 无相关文档时明确拒答；
- 用户 A 无法通过任何查询检索用户 B 的文档；
- 文档提示词注入测试全部被隔离。

### 4.8 推荐周期

专注开发约 3～5 周；边学边开发约 5～8 周。

## 5. V5：组合智能与主动基金助手

### 5.1 版本目标

把系统从“用户问一次、系统答一次”升级为能够持续观察组合风险并主动生成报告的基金助手。

### 5.2 组合分析

- 多组合管理；
- 持仓收益和时间加权收益；
- 资金加权收益 XIRR；
- 行业暴露；
- 股票/债券资产暴露；
- 基金持仓重合度；
- 单基金、单行业和单管理人集中度；
- 组合波动率、最大回撤和夏普；
- 风险贡献；
- 相关性矩阵；
- 压力测试和情景分析；
- 定投回测；
- 再平衡模拟，但不直接发起交易。

### 5.3 主动任务

- 每日净值同步；
- 自选和持仓异常波动提醒；
- 最大回撤阈值提醒；
- 基金经理变更提醒；
- 季报和公告更新提醒；
- 组合集中度变化提醒；
- 周报、月报和季度报告；
- 任务去重、静默期和通知重试；
- 邮件、企业微信、飞书或 Webhook 通知。

### 5.4 事件驱动

```text
Provider Sync
→ Data Changed Event
→ Rule Engine
→ Analysis Task
→ Agent Report
→ Evidence Validation
→ HITL（涉及私有导出或外发时）
→ Notification
```

建议引入：

- Kafka、RabbitMQ 或 Redis Streams；
- Outbox Pattern；
- 幂等消费者；
- 失败重试和死信队列；
- 通知模板版本；
- 用户通知偏好。

### 5.5 多 Agent（可选）

只有 V3 和 V4 稳定后才增加：

- Data Agent：检查数据新鲜度和口径；
- Quant Agent：调用确定性指标和回测工具；
- Document Agent：检索公告和季报；
- Risk Agent：检查组合风险；
- Report Agent：汇总已经验证的证据。

Supervisor 只能编排，不能自己编造指标。多 Agent 的目的必须是职责隔离和并行处理，而不是为了增加“Agent 数量”。

### 5.6 V5 验收标准

- 组合收益能够由交易流水复算；
- 报告中的数字全部来自确定性 Tool；
- 相同事件不会重复发送通知；
- 报告能列出数据时间、算法版本和证据；
- 通知失败可以重试并进入死信；
- 用户可以关闭规则、设置静默期和删除通知目标；
- 外发含持仓的报告必须经过 HITL；
- 回测明确避免未来函数和幸存者偏差。

### 5.7 推荐周期

专注开发约 4～6 周；边学边开发约 6～10 周。

## 6. V6：生产级与平台化

### 6.1 版本目标

让项目达到可部署、可扩容、可观测、可治理的生产平台标准。这一版不是继续增加业务功能，而是证明系统能够稳定运行。

### 6.2 服务拆分建议

不要一开始就拆微服务。只有压测和故障边界证明有必要时，才逐步拆分：

```text
api-service
agent-worker
data-sync-worker
knowledge-worker
notification-worker
```

共享规则：

- Domain 模型不能被不同服务各自复制修改；
- 事件必须带 Schema Version；
- 跨服务请求带 Trace ID、User ID 和 Idempotency Key；
- 数据所有权必须明确；
- 不能让所有服务共享并随意修改同一批表。

### 6.3 部署和弹性

- Docker 多阶段构建；
- Kubernetes Deployment、Service、Ingress；
- ConfigMap 和 Secret；
- Readiness、Liveness 和 Startup Probe；
- 水平扩容；
- Worker 独立扩容；
- MySQL 主从或云数据库；
- Redis Sentinel/Cluster 或云 Redis；
- Elasticsearch/OpenSearch 集群；
- 对象存储；
- 灰度发布和快速回滚。

### 6.4 可观测性

- OpenTelemetry Trace；
- Prometheus Metrics；
- 结构化日志；
- Grafana 面板；
- Provider、数据库、缓存、模型、Tool 和 RAG 全链路；
- Agent Run、Task、Tool Call 和模型请求关联；
- Token、模型费用和用户预算；
- SLO、错误预算和告警。

关键 SLI：

- API 可用率；
- P50/P95/P99；
- Provider 成功率和数据新鲜度；
- 同步积压；
- Agent Run 成功率；
- 首 Token 时间；
- Tool 失败率；
- RAG 检索耗时；
- 通知成功率；
- 单次报告成本。

### 6.5 安全和合规

- JWT 密钥轮换；
- RBAC；
- API Rate Limit；
- CSRF/CORS/CSP；
- SQL 注入、SSRF、文件上传和依赖扫描；
- Secret 不进入日志和数据库；
- 持仓和模型上下文脱敏；
- 用户数据加密；
- 审计日志防篡改；
- 数据保留和删除策略；
- SBOM 和镜像签名；
- 依赖漏洞和许可证检查；
- 灾难恢复和备份演练。

### 6.6 测试和发布门禁

- 单元测试；
- Repository 集成测试；
- Provider 契约测试；
- Testcontainers；
- `go test -race`；
- Fuzz Test；
- Benchmark；
- Agent 固定评测；
- RAG 固定评测；
- k6 压测；
- 故障注入；
- 数据库备份恢复演练；
- CI/CD 自动回滚。

### 6.7 V6 验收标准

- 在目标并发下达到事先定义的 P95，而不是事后编造性能数字；
- 单个 Worker 崩溃不会丢失任务；
- Redis 故障时核心查询能够降级；
- 模型故障时基金基础查询和指标仍可用；
- Provider 故障时显示已有数据和新鲜度；
- 数据库备份能够实际恢复；
- 所有生产 Secret 都由 Secret Manager 提供；
- 每个简历性能数字都有测试报告和复现命令。

### 6.8 推荐周期

专注开发约 3～6 周；生产环境治理需要持续迭代。

## 7. 版本之间的依赖关系

| 能力 | 前置版本 | 原因 |
| --- | --- | --- |
| 持久化 Agent DAG | V2 | 需要稳定数据库和用户边界 |
| 长期 Memory | V2 | 需要真实用户和数据删除能力 |
| 大规模 RAG | V2、V3 | 需要权限、任务系统和 Agent 证据协议 |
| 主动报告 | V3、V4 | 需要可恢复 Agent 和可信文档引用 |
| 多 Agent | V3、V4 | 单 Agent Runtime 和评测未稳定前没有增加复杂度的价值 |
| 微服务拆分 | V5 | 必须先通过实际负载识别边界 |

## 8. 每个版本统一的完成标准

每个版本只有同时满足以下条件才能标记完成：

1. 有一条可操作的用户链路；
2. 有数据库 Migration；
3. 有 API 文档；
4. 有单元和集成测试；
5. 有失败和降级路径；
6. 有权限和审计；
7. 有 Metrics 和日志；
8. 有固定验收数据；
9. README 已更新；
10. 简历数字可以通过脚本复现。

## 9. 推荐里程碑

```text
M1：V2 多源数据、账户、组合和同步治理
M2：V3 Eino + 持久化 Agent Runtime + HITL
M3：V4 Elasticsearch 混合 RAG + 引用与评测
M4：V5 组合风险、事件驱动和主动报告
M5：V6 Kubernetes、OTel、压测、安全和交付报告
```

如果目标是尽快找工作，建议至少完成到 V3；如果目标是让项目成为 Agent 方向的核心简历项目，建议完成到 V4；V5 和 V6 更适合体现高级后端、架构和生产治理能力。
