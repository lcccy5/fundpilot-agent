# fund-knowledge 可读性审计

本模块只有领域模型、切块、混合检索、上下文预算和入库状态机，不连接 Spring、数据库或搜索引擎。本次只改了 `fund-knowledge` 的主代码与测试，以及这份说明。生产行为没有为了测试而改动。

## 空文档

注册命令里的 null 正文会先变成空数组，随后和 0 字节正文一样被拒绝，消息为 `document size must be between 1 byte and 50 MB`。拒绝发生在写原文和调用仓库之前。

解析结果的字符总数按各页 `content.length()` 相加，空白也算。总数为 0 时，处理流程把版本改成 `OCR_REQUIRED`，错误码同名，不安排重试，也不走通用失败分类。只有空白的正文字符总数大于 0，会进入切块；规范化后没有达标切片时抛出 `No searchable text chunks were produced`，分类为不可重试的 `INVALID_DOCUMENT`。

切块器跳过空白页。短于最小字符数的残留不会成片，跨页时只是接到下一页开头。全部页都没有草稿时，末尾那段残留还会再用空标题和页码 1 试一次，但同一条最小长度仍然生效，所以纯短文的结果还是空列表。传入 null 文档会抛空指针，不视为空文档。

## 超长中文

切块按「词元数 × 2」换成 UTF-16 字符数。句子只在 `。！？；!?;` 和换行处断开，中文逗号和英文句号不断句。单句长于最大字符数时不在句内再切，整句成为超长切片。重叠尾巴在下一句放不下时会先单独成片，超长句本身仍然不被拆开。

去重后的草稿数在每一页结束时检查。超过 `maxChunks` 抛出 `Document exceeds maximum chunk count`。完全相同的句子只保留一次，不占用这个上限。处理流程看到这条异常时，消息对不上「无效文档」关键字：尝试次数不到 3 次则按依赖失败重试，退避秒数是 `min(600, 10 << min(5, attempts))`；达到 3 次则 `RETRY_EXHAUSTED`。

检索查询按 UTF-16 长度计，超过 500 即拒绝，刚好 500 可以检索。注册正文超过 50MB 即拒绝。向量条数不一致的消息是 `EMBEDDING_COUNT_MISMATCH`，同样走重试，不会因为没有 `DIMENSION` 而被当成维度终态。

## 重复入库

本模块不比较历史版本。通过校验的命令会先把字节写入 `RawDocumentStore`，再把哈希交给 `DocumentMetadataRepository.register`。`duplicate` 完全由仓库返回，服务原样交回，所以重复内容仍会先落一次原始字节。外部文档号为空白且来源 URI 为 null 时，在写存储前拒绝，因为没有版本幂等键。重复内容不抛冲突异常。

切块里的「重复」是另一件事：规范化后的正文完全相同则只留第一片。

## 无命中

词法路和向量路都为空时，融合、重排和预算得到空列表。检索仍返回新的检索号和空警告，不抛异常。某一路返回 null 时，融合器把该路当作无命中。两路都为 null 时结果为空。

重排候选为空，或 `topK` 为 0 时，返回空列表。没有共同二元组、查询为 null，或查询短于两个字符时，重叠分为 0，候选仍按原分数的 5% 排序，不会被丢掉。重排抛出运行时异常（包括负的 `topK`）时，检索改用融合结果，并只追加警告 `RERANK_DEGRADED`。构造检索服务时若把重排条数设为 0，正常重排会得到空列表且没有该警告，整次检索变成无命中。

`KnowledgeSearchQuery` 把小于等于 0 的 `topK` 改成 6，大于 10 的改成 10。因此调用方传 0 并不会得到空结果。直接调用预算分配器时，`topK` 小于等于 0 才会一片都不收。

## 缺失引用

页标题为 null 时切块写成空串。来源名称、来源 URI、文档标题和发布日期允许为 null，并原样进入切片。检索、重排、融合和预算都不因这些字段缺失而丢弃切片，也不追加警告。

相邻切片合并时，标题、基金代码、文档标题、发布日期和来源取左侧，页码取两侧极值。右侧标题和来源不会补上左侧的空引用。合并后的顺序号仍是左侧的顺序号，连续三片只会变成「第一片+第二片」再另留第三片。

本模块的 `KnowledgeNotFoundException`、`KnowledgeInvalidArgumentException`、`KnowledgeConflictException` 和 `KnowledgeUnavailableException` 由仓库或外层边界抛出。切块、检索和注册在模块内仍抛 `IllegalArgumentException` 或 `IllegalStateException`。

## 上下文预算

空候选返回空列表。相同 `contentSha256` 只留第一次，重复项不占预算。单片词元数放不进剩余预算时跳过该片，继续看后面更小的片，结果可以不连续。`tokenCount` 按调用方给定的值使用，0 也会被收下。

条数达到 `topK` 后停止，但停止前仍会尝试把下一片合并进最后一片。相邻的定义是同一版本、顺序号刚好加一，且右侧起始页不超过左侧结束页的下一页。合并还要求新片单独放得进剩余预算，并且两侧词元之和不超过完整预算，而不是剩余预算。

混合检索在重排之后用构造时的词元上限和查询里已经钳制过的 `topK` 做这次裁剪。

## 遗留问题

下面这些没有改，改了就会改变现有行为或越出本模块。

- 词元预算是固定的两倍字符，重叠按 UTF-16 单元截取，词元估算却按码点。两把尺子不一致。
- 超长句不拆开，重叠尾巴可能单独再成一片，页内草稿要整页切完才检查上限。
- 去重是整段字符串相等，逐片扫描已有草稿。
- 页结束后若残留短于最小长度，最后那次补救调用仍会被同一条最小长度丢掉。
- 二元组按 Java `char` 切，不按码点。重排算出的新分数不写回命中对象，后面的预算看到的仍是原分数。相等分数只靠流排序的稳定性。
- 失败分类靠异常消息里的英文片段。检查点、损坏文件和不受支持的格式必须自己带上约定单词，否则会变成可重试错误。无法识别的步骤名会退回 `REGISTERED` 并重做。
- 处理流程不调用 `IngestionStatus.canTransitionTo`，只把期望状态交给仓库。
- 写别名把读别名里的 `_read` 全部替换成 `_write`。条数不一致时创建重建仍返回视图，不抛异常。
- 检索服务不校验各路 `topK`。重排条数为 0 会静默变成无命中，为负则会降级并退回未截断的融合结果。
- 注册测试里原先未使用的索引替身已从该测试类移除，避免把没人调用的双写留在可读性改动里。
